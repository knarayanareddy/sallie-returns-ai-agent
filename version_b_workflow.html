ReturnCaseState — Schema Comparison: Version A vs. Version B

Version A — Single Schema

One schema, mutated in place by the single orchestrator's nodes. Simpler — no inter-agent version negotiation.

# Version A — single writer, sequential mutations # All mutations by the one orchestrator runtime case_id: str customer_id: Optional[str] origin_store_id: str purchase_date: Optional[datetime] # datetime, not str receipt_id: Optional[str] items: List[ReturnItem] resolution_type: Literal["REFUND","EXCHANGE","DEFECT_REMEDY","PENDING_REVIEW"] proof_verified: bool = False defect_detected: bool = False condition_verdict: Optional[ConditionVerdict] # NEW: structured CV output hold_reservation_id: Optional[str] supplier_claim_id: Optional[str] escalation_reason: Optional[str] customer_notification_status: Literal["NOT_SENT","SENT","FAILED"] = "NOT_SENT" # NEW dead_letter_reason: Optional[str] # NEW: for expired lock path closed: bool = False closed_at: Optional[datetime] agent_audit_log: List[AgentDecisionLogEntry] # NEW: observability

Version B — Versioned Schema, Agent-Owned Fields

Same base schema but: (1) version field for agent-to-agent negotiation; (2) each agent declares which fields it owns; (3) schema version must match before merge.

# Version B — schema versioning + agent ownership # Orchestrator owns full schema; agents declare owned_fields schema_version: Literal["1.0"] # NEW: required for agent merge case_id: str # Owned by Orchestrator customer_id: Optional[str] # Owned by Intake Agent origin_store_id: str # Owned by Intake Agent purchase_date: Optional[datetime] # Owned by Intake Agent receipt_id: Optional[str] # Owned by Intake Agent items: List[ReturnItem] # Owned by Intake Agent resolution_type: Literal[...] # Owned by Orchestrator (policy routing) proof_verified: bool # Owned by Cross-Store Agent defect_detected: bool # Owned by Warranty Claims Agent hold_reservation_id: Optional[str] # Owned by Inventory Agent supplier_claim_id: Optional[str] # Owned by Warranty Claims Agent escalation_reason: Optional[str] # Owned by Orchestrator owned_by: dict[str, str] # NEW: field → agent_name mapping last_modified_by: str # NEW: which agent last wrote modified_at: datetime # NEW: timestamp of last write customer_notification_status: Literal[...] # Owned by Orchestrator closed: bool # Owned by Orchestrator agent_audit_log: List[LogEntry] # Per-agent entries; owned by Orchestrator
Why versioning matters in B: When Warranty Claims Agent writes defect_classification, it stamps last_modified_by = "warranty_claims_agent" and modified_at. If the schema changes (e.g., a new field added), agents can check schema_version before merging. Prevents silent field collisions when multiple agents touch the same case concurrently.

Version A vs. Version B — Head-to-Head for Group Decision

Read this with your team. The question is not which is "better" in the abstract — it's which one matches your current infrastructure, volume, and team structure.

Version A — Single Orchestrator · 6 Nodes

  • Faster to first value: Build case DB + receipt lookup + policy routing first. One state machine, one prompt context.
  • Simpler to debug: One agent runtime means one log stream. When something goes wrong, you know where to look.
  • Lower build cost: One agent to build, test, and deploy. No inter-agent state contracts, no schema versioning.
  • Natural for 4 stores: Four specialized agent runtimes for four stores is over-engineering at this scale.
  • HITL is a node, not a shared resource: Simpler — escalations go to one queue, re-entry is explicit in the state machine.
  • No agent-level isolation: If the orchestrator's defect node has a bug, the refund path is not affected (separate nodes) but there's no runtime isolation.
  • Harder to scale per-agent independently: Adding more sophisticated defect classification means upgrading the whole orchestrator deployment.
  • Observability is pipeline-level: You can see where the pipeline failed; harder to attribute a specific bad decision to a specific capability.
  • Best first build: Start here regardless. Version B is a migration path from A, not an alternative starting point.

Version B — Four Agents + Orchestrator

  • Agent-level isolation: Warranty Claims Agent can be upgraded, tested, and redeployed without touching the Intake Agent.
  • Independent agent evals: Each agent has its own accuracy metrics. You know the Cross-Store Agent is at 95% recall and the Defect Agent is at 82% — and can act on each independently.
  • Team scaling: If a second developer joins, they can own the Inventory Agent while another owns the Warranty Claims Agent. Clear ownership boundaries.
  • Parallel defect track: Warranty Claims Agent runs concurrently with the customer remedy path. Customer gets their refund while RMA is assembled — not sequential.
  • Schema versioning: When you need to add fields (e.g., a new supplier portal requires additional metadata), you version the schema and agents negotiate — no silent field collisions.
  • Multi-store scaling: If Sallie se Schoenen opens store 5, 6, 7 — the Cross-Store Agent's federation scope expands without touching the Intake Agent.
  • Higher build cost: Four agent runtimes, inter-agent state contracts, schema versioning, per-agent observability. Significantly more to build.
  • Inter-agent debugging: A failed case means tracing state through multiple agents. Requires observability investment from day one.
  • Orchestrator is still the single point of control: If it goes down, everything stops — same as Version A. The multi-agent separation doesn't fix that.
  • Premature at 4 stores: Unless you already have the infrastructure (federated POS API, WMS with lock semantics, supplier portal API), the extra complexity of Version B is not justified by the current scale.
